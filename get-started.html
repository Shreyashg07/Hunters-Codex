Codex / Get Started

Before you open a target

Four things worth two minutes each: how the checklist is meant to be used, what the severity tags actually mean, the rules every entry in this Codex assumes you're following, and how it grows.

1 — How to work through a directory

Each directory is ordered roughly by how cheap the check is to run. Open the entries, work top to bottom on a fresh target, and use the checkbox on each one to mark it tested — your progress is saved in this browser via localStorage, per directory, so you can close the tab and pick back up later.

Every entry follows the same five sections: Description (what the bug is), Impact (why it matters), Severity (realistic range, not a worst-case fantasy), Steps to Reproduce (exact commands/payloads), and Reporting Guidance — read that last section before you file anything. It's written to stop duplicate/informational submissions as often as it is to encourage good ones.

2 — Severity legend

Used consistently across every entry, loosely CVSS-flavoured but written for realistic bug-bounty triage rather than a worst-case theoretical score:

CRITICAL — direct path to full compromise: RCE, auth bypass, mass account takeover.
HIGH — serious, usually single-account takeover or major data exposure.
MEDIUM — real impact, but needs a condition or chain to matter.
LOW — genuine but limited; often a hygiene/hardening gap.
INFO — worth knowing, rarely worth a standalone report.

3 — Rules every entry assumes

  • Only test targets you're explicitly authorized for — an active bug bounty or VDP scope, or your own infrastructure.
  • Read the program's scope and policy first — DoS, social engineering, and physical testing are commonly excluded, and several entries here (long-password DoS, SPF) are frequently affected by that.
  • Use your own test accounts for anything destructive. Never run write/delete/reset actions against a real victim's account or data to "prove" a bug.
  • Stop at proof. Confirming you can read one record, not the whole database, is enough for a report — mass data extraction isn't necessary and usually isn't welcome.
  • Report through the program's disclosed channel, respect embargo/disclosure timelines, and never discuss an unresolved finding publicly.

4 — How this grows

Five directories are live now — the three Low Hanging Fruits parts, Broken Access Control (CSRF, IDOR/BOLA), and Security Misconfiguration (subdomain takeover). The home page's remaining roadmap cards (Injection Deep Dive, API & Business Logic) are next. Each new directory drops in as its own file under /categories/ with a matching /assets/js/data-*.js — same content shape as everything above (plus an optional decision tree and Burp walkthrough section for the deeper classes), so the checklist stays consistent as it expands.

If you're reading this from the repo: see README.md for the exact steps to add a new directory or append an entry to an existing one.
